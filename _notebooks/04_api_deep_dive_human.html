Part 4 — Core API Deep-Dive (Human Example)

Last updated: 2026-11-12

This notebook is a hands-on tutorial of the public IDTrack API using human.

Learning objectives

  • Create the idtrack.API façade and understand what it wraps.

  • Convert single identifiers (time travel + optional external outputs).

  • Convert batches and summarize outcomes (1→0 / 1→1 / 1→n).

  • Request explanation payloads for audit trails.

  • Learn advanced knobs (external bridging, ambiguity strategy, assembly awareness).

  • Learn introspection helpers (available databases, assemblies, releases, active ranges).

Prerequisite: 03_initialization_graph.ipynb (Part 3) is recommended so the graph loads from cache.

4.1 — The API Facade

idtrack.API is the user-facing entry point. It handles:

  • organism resolution (species names, common names and taxon IDs of the supported organisms: human, mouse, pig, rhesus and cynomolgus macaque)

  • building or loading a graph snapshot (the reproducible snapshot boundary)

  • conversion helpers like convert_identifier(...) and convert_identifier_multiple(...)

In this notebook we build (or load) the human snapshot, then use it for the rest of the examples.

Expected result: after the setup cell runs, api.track exists and conversions become available.

1

from __future__ import annotations

import os
from pathlib import Path

import idtrack

LOCAL_REPOSITORY = Path(os.environ.get('IDTRACK_LOCAL_REPO', 'idtrack_cache'))
LOCAL_REPOSITORY.mkdir(parents=True, exist_ok=True)

api = idtrack.API(local_repository=str(LOCAL_REPOSITORY))
api.configure_logger()

organism, latest_release = api.resolve_organism('human')
SNAPSHOT_RELEASE = 115  # pinned (latest_release is Ensembl's newest release)

api.build_graph(organism_name=organism, snapshot_release=SNAPSHOT_RELEASE)
print('Ready:', organism, 'snapshot', SNAPSHOT_RELEASE)

If you see no_corresponding=True, the input could not be matched to any identifier of the graph. IDTrack already tries the letter-case and separator variants (tp53, HLA_A for HLA-A) and says in match how the identifier matched; graph_id is the identifier of the graph it was read as, and from_release the release at which it was read. Without from_release, an identifier is read at the target release if it exists there, otherwise at the latest release at which it exists.

alternative_locus_genes lists genes the identifier also leads to that are copies on alternative loci, assembly patches or LRG records (LRG_321.1 for TP53): they are reported apart from the answer, which holds the gene of the reference sequence.

4.2.4 Understanding the result dictionary

Key fields (the docstring of API.convert_identifier lists every field):

  • query_id: exactly what you typed

  • graph_id: the identifier of the graph it was read as; match: how it matched (exact, case, separator, version, synonym:..., version_newer_than_graph)

  • from_release: the release it was read at; from_release_inferred: chosen by IDTrack (no from_release given); from_release_fallback: the from_release you gave does not hold the identifier, so it was read where the graph holds it

  • target_id: list of outputs (can be 0, 1, or many), in a fixed order; last_node: [gene, target] pairs

  • ambiguous: more than one target; tie: the best answer is shared by several genes or targets equal in all evidence

  • alternative_locus_genes: copies on alternative loci and patches reported apart from the answer

  • no_corresponding: input didn’t match any identifier of the graph (known_versions lists the versions that exist when you gave an Ensembl id with a version the graph does not hold)

  • no_conversion: input matched, but no gene at the target release descends from it

  • no_target: genes were reached, but none has an id in the requested database (the targets are then their Ensembl ids); no_target_genes: genes without such an id when others have one

Important: target_id is a list because ambiguity is real and common. Every result is plain data (json.dumps works on it).

4.2.5 Versions, spelling variants and releases

A few identifiers that show how IDTrack reads what you give it:

  • an Ensembl id with a version that never existed is not answered with another version’s gene (known_versions names the ones that exist), except a version higher than all the graph holds of an id still alive at the snapshot, which may come from a newer release and is read as the latest version;

  • a from_release at which the graph does not hold the identifier is set aside and reported (from_release_fallback), while a release that is not a release of the graph at all is an error that names the valid ones.

4.2.6 Ambiguity control: strategy=’best’ vs strategy=’all’

  • strategy='best' (default): returns the best answer: one target, or, when several genes or targets are equal in all evidence, all of them in ascending order of gene and target id with tie=True

  • strategy='all': returns all targets IDTrack found, best first

Use 'all' when you are doing QC or want to inspect ambiguous mappings.

4.4 — Explainability & Auditability

When you set explain=True, the result includes a the_path field: one entry per [gene, target] pair of last_node, with the gene the identifier was read as (entry_gene), the number of bridges through external identifiers the search needed (external_jump; 0 is Ensembl’s history alone), the releases between leaving one gene and entering the next over those bridges (external_gap), the product of Ensembl’s mapping scores along the history (score), and the edges walked (edges): [source, target, key] for a step of Ensembl’s history in walking order, [source, target, 0, release] for a cross-reference followed at that release.

4.5 — Advanced Conversion Options

api.convert_identifier(...) is a convenience wrapper around api.track.convert(...).

Use the high-level API most of the time. But if you need full control (whether external bridging is allowed, the search budget, deeper path diagnostics), you can call Track.convert directly. It is strict where the API is forgiving: a from_release at which the identifier does not exist raises idtrack.InactiveAtReleaseError (naming the releases where it exists), and an unknown version raises idtrack.UnknownVersionError.

4.5.1 Best vs all (selection strategy)

  • strategy='best' returns the best answer: one target, or the targets that are equal in all evidence, as a tie (tie=True), in a fixed order.

  • strategy='all' returns all targets reached, best first (useful for ambiguity-aware pipelines).

4.5.2 Controlling external bridging

The search follows Ensembl’s history first. Only when that leads to no gene at the target release does it pass through an external identifier or a transcript that two genes carried (a bridge): at most two bridges, the fewest possible, in the order of time, never through clone-based names or hyper-connected identifiers. external_jump in the result says how many bridges were used. Power users can switch bridging off with go_external=False on Track.convert. The search is bounded: each state is visited once, and a call that needs more than its budget (Track.search_budget_states, Track.search_budget_seconds) raises idtrack.SearchBudgetExceededError.

4.5.3 Hyperconnected nodes

Some external identifiers are carried by many genes at the same time (RFAM families, U6, 5S_rRNA, snoRNA names): more than TheGraph.genes_at_once_threshold (5) genes in one release. They name a kind of gene, not a gene, so they are never used as bridges and are not counted as annotation of a gene. They can still be queried and returned.

4.5.4 Assembly-aware conversions

In IDTrack, genome assemblies are part of the graph. This is crucial when you integrate datasets that were annotated with different references (for example, a GRCh37-based GTF and a GRCh38-based GTF).

A conversion uses, at every release, the assembly Ensembl maintained at that release (human: NCBI36 up to release 54, GRCh37 up to 75, GRCh38 from 76). The parallel GRCh37 of later releases is not walked; its ids are in the graph as ids to convert from. The final conversion into a database is made on the assembly of the target release, so a conversion to release 70 returns the HGNC symbols of GRCh37 at release 70.

Practical consequences:

  • You can feed identifiers originating from older builds and harmonize them into one target space (a release of your snapshot).

  • External databases are read for the assembly they belong to; an id is returned as its database wrote it at the target release.

Example (advanced):

api.track.convert(
    from_id='TP53',
    from_release=None,
    to_release=SNAPSHOT_RELEASE,
    final_database='HGNC Symbol',
    go_external=True,
    return_path=True,
    from_database='HGNC Symbol',  # read the identifier as an id of this database only
)

4.6 — Introspection & Discovery

These helpers answer practical questions like:

  • Which external databases are available in my current graph?

  • Which genome assemblies are represented?

  • What Ensembl release range does my snapshot cover?

  • When was a given identifier active across releases?

The next cell demonstrates the most useful introspection calls.
