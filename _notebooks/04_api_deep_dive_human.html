Part 4 — Core API Deep-Dive (Human Example)

Last updated: 2026-11-12

This notebook is a hands-on tutorial of the public IDTrack API using human.

Learning objectives

  • Load a graph into idtrack.API and understand what it wraps.

  • Convert single identifiers (time travel + optional external outputs).

  • Convert batches and summarize outcomes (1→0 / 1→1 / 1→n).

  • Request explanation payloads for audit trails.

  • Learn advanced knobs (external bridging, the ranking of candidates, search budgets, assembly awareness).

  • Learn introspection helpers (available databases, assemblies, releases, active ranges).

Prerequisite: 03_initialization_graph.ipynb (Part 3) is recommended so the graph loads from cache.

4.1 — The API Facade

idtrack.API is the user-facing entry point. It handles:

  • organism resolution (species names, common names and taxon IDs of the supported organisms: human, mouse, pig, rhesus and cynomolgus macaque)

  • building or loading a graph snapshot (API.build, API.load; the reproducible snapshot boundary)

  • conversions: convert(...) and convert_many(...), which return typed results (idtrack.results.ConversionResult)

In this notebook we build (or load) the human snapshot, then use it for the rest of the examples.

Expected result: after the setup cell runs, api holds the graph and conversions become available.

1

from __future__ import annotations

import os
from pathlib import Path

import idtrack
from idtrack import API

LOCAL_REPOSITORY = Path(os.environ.get('IDTRACK_LOCAL_REPO', 'idtrack_cache'))
LOCAL_REPOSITORY.mkdir(parents=True, exist_ok=True)

API.configure_logger()

organism = idtrack.organisms.resolve_organism('human')  # offline; API.ensembl_organism also asks Ensembl's newest release
SNAPSHOT_RELEASE = 115  # pinned

api = API.build(organism, SNAPSHOT_RELEASE, str(LOCAL_REPOSITORY))
print('Ready:', organism, 'snapshot', SNAPSHOT_RELEASE)


def show(result, strategy='best'):
    """Print the main fields of a conversion result and its candidates of one view ('best' or 'all')."""
    print(f'{result.query_id!r} read as {result.graph_id!r} (match: {result.match}) at release {result.from_release} '
          f'-> {result.final_database} at {result.to_release}: status={result.status}, tie={result.tie}, '
          f'decided_by={result.decided_by}')
    for c in result.view(strategy):
        print(f'  {c.gene} -> {c.target}  best={c.best} entry={c.entry_gene} bridges={c.bridges} score={c.score:.3f}')
    if result.alternative_locus_genes:
        print('  copies on alternative loci:', list(result.alternative_locus_genes))
    if result.reason:
        print('  reason:', API.reason_text(result))

Ready: homo_sapiens snapshot 115

If the status is not_found, the input could not be matched to any identifier of the graph. IDTrack already tries the letter-case and separator variants (tp53, HLA_A for HLA-A) and says in match how the identifier matched; graph_id is the identifier of the graph it was read as, and from_release the release at which it was read. Without from_release, an identifier is read at the target release if it exists there, otherwise at the latest release at which it exists.

alternative_locus_genes lists genes the identifier also leads to that are copies on alternative loci, assembly patches or LRG records (LRG_321.1 for TP53): they are reported apart from the answer, which holds the gene of the reference sequence.

4.2.4 Understanding the result

A result is an idtrack.results.ConversionResult (a frozen dataclass; its docstring lists every field):

  • query_id: exactly what you typed

  • graph_id: the identifier of the graph it was read as; match: how it matched (exact, case, separator, version, synonym:..., version_newer_than_graph)

  • from_release: the release it was read at; from_release_inferred: chosen by IDTrack (no from_release given); from_release_fallback: the from_release you gave does not hold the identifier, so it was read where the graph holds it

  • candidates: every target the search reached, ranked, the best marked (candidate.best); targets('best') and targets('all') are the target ids of the two views (view('best'), view('all'))

  • tie: the best answer is shared by several genes or targets equal in all evidence; decided_by: the criterion that put the best answer before the runner-up

  • alternative_locus_genes: copies on alternative loci and patches reported apart from the answer

  • status: converted, tie, no_target, not_found (input didn’t match any identifier of the graph), unknown_version (known_versions lists the versions that exist), no_conversion (input matched, but no gene at the target release descends from it) or error; reason says why a result has no candidate

  • no_target: genes were reached, but none has an id in the requested database (the targets are then their Ensembl ids); no_target_genes: genes without such an id when others have one

Important: there can be 0, 1 or many targets, because ambiguity is real and common. Every result is strict JSON with result.to_dict(), and ConversionResult.from_dict(...) reads it back.

4.2.5 Versions, spelling variants and releases

A few identifiers that show how IDTrack reads what you give it:

  • an Ensembl id with a version that never existed is not answered with another version’s gene (known_versions names the ones that exist), except a version higher than all the graph holds of an id still alive at the snapshot, which may come from a newer release and is read as the latest version;

  • a from_release at which the graph does not hold the identifier is set aside and reported (from_release_fallback), while a release that is not a release of the graph at all is an error that names the valid ones.

6

from idtrack.errors import InputError

    ('ENSG00000141510.5', {}),                      # an old version: read where it exists (release 54), followed to 115

    ('ENSG00000141510.25', {}),                     # newer than the graph's latest version: read as the latest version

          f"from_release={r.from_release} fallback={r.from_release_fallback} status={r.status}{known}")

4.2.6 Ambiguity: the best answer and every candidate

One conversion returns every candidate the search reached, ranked; the best answer is marked:

  • result.view('best'): the best answer: one target, or, when several genes or targets are equal in all evidence, all of them with tie=True

  • result.view('all'): all targets IDTrack found, best first; each candidate carries its ranking record (final confidence, bridges, gap, support of the entry gene, score, being the query itself, steps)

Use 'all' when you are doing QC or want to inspect ambiguous mappings.

7

result = api.convert('TP53', to_release=SNAPSHOT_RELEASE)
show(result, 'all')

4.4 — Explainability & Auditability

When you set explain=True, the result includes path, an idtrack.results.ExplainedPath: one graph per conversion with every node (its kind, label, databases, the releases at which a gene is active and the assemblies that serve them, the releases at which it lies outside the reference sequence) and every step once. A step (idtrack.results.PathStep) has its kind (entry from the identifier to the gene it stands for, history for an event of Ensembl’s id history, self_loop, bridge_near and bridge_far for the two sides of a bridge through an id two genes carried, final from the gene to its id in the final database, identity for a gene that is its own answer), the releases, Ensembl’s mapping score, the splits and merges of a history event, the databases and the assembly of a cross-reference, and the reason it was taken. Each candidate lists its steps by index: path from the identifier to the gene, final_path from the gene to the target.

11

explained = api.convert('TP53', to_release=SNAPSHOT_RELEASE, final_database='HGNC Symbol', explain=True)
best = explained.view('best')[0]
for index in best.path + best.final_path:
    step = explained.path.steps[index]
    print(f'{step.kind:<8} {step.source} -> {step.target} | release {step.release} | {", ".join(step.databases)}')

4.5 — Advanced Conversion Options

api.convert(...) checks the arguments and reads the string, then calls the engine, api.engine.convert(...) (idtrack.engine.Track.convert).

Use the high-level API most of the time; it already takes allow_bridges, budget_states and budget_seconds. The engine is strict where the API is forgiving: a from_release at which the identifier does not exist raises idtrack.errors.InactiveAtReleaseError (naming the releases where it exists), and an unknown version raises idtrack.errors.UnknownVersionError.

4.5.1 Best vs all

  • result.view('best') is the best answer: one target, or the targets that are equal in all evidence, as a tie (tie=True), in a fixed order.

  • result.view('all') is every target reached, best first (useful for ambiguity-aware pipelines); result.decided_by names the criterion that put the best answer before the runner-up.

4.5.2 Controlling external bridging

The search follows Ensembl’s history first. Only when that leads to no gene at the target release does it pass through an external identifier or a transcript that two genes carried (a bridge): at most two bridges, the fewest possible, in the order of time, never through clone-based names or hyper-connected identifiers. candidate.bridges says how many bridges were used. Switch bridging off with allow_bridges=False. The search is bounded: each state is visited once, and a call that needs more than its budget (idtrack.settings.SearchSettings: 200,000 states and 30 s by default; budget_states= and budget_seconds= of a call) raises idtrack.errors.SearchBudgetExceededError.

4.5.3 Hyperconnected nodes

Some external identifiers are carried by many genes at the same time (RFAM families, U6, 5S_rRNA, snoRNA names): more than the hyper-connectivity threshold of the graph (idtrack.settings.GraphSettings, 5) genes in one release. They name a kind of gene, not a gene, so they are never used as bridges and are not counted as annotation of a gene. They can still be queried and returned.

4.5.4 Assembly-aware conversions

In IDTrack, genome assemblies are part of the graph. This is crucial when you integrate datasets that were annotated with different references (for example, a GRCh37-based GTF and a GRCh38-based GTF).

A conversion uses, at every release, the assembly Ensembl maintained at that release (human: NCBI36 up to release 54, GRCh37 up to 75, GRCh38 from 76). The parallel GRCh37 of later releases is not walked; its ids are in the graph as ids to convert from. The final conversion into a database is made on the assembly of the target release, so a conversion to release 70 returns the HGNC symbols of GRCh37 at release 70.

Practical consequences:

  • You can feed identifiers originating from older builds and harmonize them into one target space (a release of your snapshot).

  • External databases are read for the assembly they belong to; an id is returned as its database wrote it at the target release.

Example (advanced):

api.convert(
    'TP53',
    to_release=SNAPSHOT_RELEASE,
    final_database='HGNC Symbol',
    from_database='HGNC Symbol',  # read the identifier as an id of this database only
    explain=True,
)

4.6 — Introspection & Discovery

These helpers answer practical questions like:

  • Which external databases are available in my current graph?

  • Which genome assemblies are represented?

  • What Ensembl release range does my snapshot cover?

  • When was a given identifier active across releases?

The next cell demonstrates the most useful introspection calls.

4.7 — Practical advice (the kind that saves you a week)

  1. Always record your snapshot boundary (release) in your analysis notes.

  2. If you share results, share the external YAML too.

  3. When mapping is ambiguous, do not hide it — decide how your pipeline should handle 1→n mappings.

  4. For scRNA-seq harmonization, prefer stable namespaces (Ensembl IDs) before switching to symbols.
