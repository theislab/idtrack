Part 3 — Graph Initialization & Management

Last updated: 2026-11-12

This notebook shows how to build and cache an IDTrack graph snapshot for:

  • homo_sapiens (human)

  • mus_musculus (mouse)

  • sus_scrofa (pig)

  • macaca_mulatta (rhesus macaque) and macaca_fascicularis (cynomolgus macaque)

A graph build is the most expensive step. The good news:

  • you usually do it once per organism + snapshot boundary + external YAML configuration

  • the snapshot is multi-assembly (human has overlapping GRCh38/GRCh37; mouse, pig and the macaques are clean-handoff by release, and the ids of their earlier assemblies are in the graph too)

  • then you load the graph file from your local repository in a few seconds, without network

Learning objectives

  • Build (or load) a graph snapshot for each organism.

  • Verify that the snapshot exists on disk.

  • Learn practical graph-management habits (reload vs rebuild, cache hygiene).

Prerequisite: every supported organism ships a default external YAML; run 02_prepare_new_external_yaml.ipynb first only if you want your own selection of external databases.

3.0.1 — Sanity check: which external YAML files will be used?

Every supported organism ships a packaged default (idtrack/default_config/<organism>_externals_modified.yml); a file of the same name in your local repository (created in Part 2) takes precedence.

3

# External YAML presence: local repository first (created in Part 2), else the packaged default
DEFAULT_CONFIG = Path(idtrack.__file__).parent / 'default_config'


def _yaml_status(organism):
    local = LOCAL_REPOSITORY / f'{organism}_externals_modified.yml'
    shipped = DEFAULT_CONFIG / local.name
    if local.exists():
        return True, 'OK', local.name
    if shipped.exists():
        return True, 'OK (packaged default)', local.name
    return False, 'MISSING (create it in Part 2)', local.name


HAS_HUMAN_YAML, *_human = _yaml_status('homo_sapiens')
HAS_MOUSE_YAML, *_mouse = _yaml_status('mus_musculus')
HAS_PIG_YAML, *_pig = _yaml_status('sus_scrofa')

for status, name in (_human, _mouse, _pig):
    print(status.ljust(55), name)

3.1–3.3 — Build graph snapshots (one per organism)

The canonical pattern is:

  1. resolve organism name

  2. pick (and pin) the snapshot release

  3. api.build_graph(...): loads the graph file if it is in the local repository, builds and saves it otherwise

  4. inspect + reuse

The primary assembly of a graph is the organism’s preferred assembly that has the snapshot release (human GRCh38, mouse GRCm39, pig Sscrofa11.1, rhesus Mmul_10, cynomolgus 6.0 at release 115); it is part of the graph file’s name.

We do this for each organism below. If you only need one organism, run only that section. The tutorials pin the snapshot release to 115: resolve_organism returns Ensembl’s newest release, which changes every few months, and a graph is built per snapshot.

3.1 — Human graph initialization (multi-assembly)

The human graph has GRCh38 as its primary assembly (assembly key 38): conversions use, at each release, the assembly Ensembl maintained at that release (NCBI36 36 to release 54, GRCh37 37 to 75, GRCh38 from 76), and the GRCh37 ids of later releases are in the graph as ids to convert from.

This is what enables atlas-building workflows where different datasets were annotated with different genome builds, but you want one unified identifier space.

3.4 — Rhesus and cynomolgus macaque graph initialization (clean handoff)

Both macaques are clean-handoff species:

  • rhesus (macaca_mulatta): MMUL_1 (key 1, releases 48–85) → Mmul_8.0.1 (801, 86–97) → Mmul_10 (10, 98+)

  • cynomolgus (macaca_fascicularis): Macaca_fascicularis_5.0 (5, 91–102) → 6.0 (6, 103+)

The snapshot graph links the assemblies through Ensembl’s own history (e.g. rhesus 85 → 86 and 97 → 98), so identifiers from an older genome build convert to the current one. Gene symbols are VGNC symbols on the current assemblies and HGNC symbols on the older ones; both are enabled in the shipped YAML files. Rhesus and cynomolgus are two organisms and two graphs.

The full builds read every release since 48 (rhesus) or 91 (cynomolgus); they work over HTTPS alone (IDTRACK_ENSEMBL_ACCESS=https).

3.5 — Graph management (all species)

Reloading vs rebuilding

  • api.build_graph(...) is safe to call repeatedly.

    • If the graph file is in the local repository, IDTrack loads it: from the file alone, with no table, no database manager and no network.

    • If it does not exist yet, IDTrack builds it (slow, first time only) and saves it.

  • One idtrack.API holds one graph: build_graph for another organism replaces the graph of the object. Keep one API per organism if you need several at once.

What a graph file is

  • One .npz file per graph, graph_<organism>_assembly<primary assembly>_min<first release>_max<snapshot>_narrow.npz: graphs of different organisms, snapshots and primary assemblies sit side by side in one local repository.

  • The file records what it was built from: the selection of external databases that takes effect (from your external YAML), the organism table, the graph format and the package version, the tables, and the corrections made to Ensembl’s id history (api.track.graph.graph['manifest']). Loading a file under the expected name that was built from something else (another YAML selection, another organism table, an older graph format) raises idtrack.GraphMismatchError, which names the differences: IDTrack never answers from another graph and never starts a build of hours on its own. To build it again, move the file away and call build_graph.

  • Graph files of IDTrack 0.0.5 (graph_*.pickle) and its table cache (<organism>_assembly-<key>.h5) are not read; build the graphs again with this version.

Cache hygiene

Your local repository accumulates:

  • downloaded tables (idtrack_tables/<organism>_assembly-<key>/, one file per table; a table records what it depends on, so changing the YAML or the window never serves a stale table and nothing has to be deleted by hand)

  • graph files (graph_*.npz)

  • your external YAML files

Tip: Treat your local repository as project infrastructure. Keep it stable so you get the benefits of caching.

Switching organisms / profiles

A graph is specific to:

  • organism

  • snapshot boundary (max release) and window

  • the external databases its YAML selects (<organism>_externals_modified.yml of the local repository, or the shipped default)

To compare two selections of external databases, use one local repository per selection (the YAML file name is fixed per repository; see Part 7).

Performance tips

  • Keep your external YAML allowlist small to reduce ambiguity and the size of the downloads.

Warning: Deleting the tables of a local repository means downloading them again for the next build.
