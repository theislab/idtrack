Reporting Bugs

Found a bug? Please report it on the Issue Tracker.

A good bug report includes:

  1. Summary - A clear, concise description of the problem

  2. Environment - Python version, IDTrack version, operating system

  3. Steps to reproduce - Minimal code example that triggers the bug

  4. Expected behavior - What you expected to happen

  5. Actual behavior - What actually happened (include error messages)

Bug Report Template

## Environment
- IDTrack version: 0.0.x (run `python -c "import idtrack; print(idtrack.__version__)"`)
- Python version: 3.12.x (run `python --version`)
- OS: Ubuntu 22.04 / macOS 14.x / Windows 11

## Description
A clear, concise description of what the bug is.

## Steps to Reproduce
```python
import idtrack

# Minimal code that triggers the bug
api = idtrack.API(local_repository="./cache")
# ...
```

## Expected Behavior
What you expected to happen.

## Actual Behavior
What actually happened. Include the complete error traceback if applicable.

## Additional Context
Any other context about the problem (screenshots, related issues, etc.).

Requesting Features

Have an idea for a new feature? Open an issue on the Issue Tracker with:

  1. Use case - Describe the problem you’re trying to solve

  2. Proposed solution - Your suggested approach

  3. Alternatives considered - Other approaches you’ve thought about

  4. Impact - Who would benefit from this feature

Tip

It’s a good idea to open an issue before starting work on a feature. This allows maintainers to discuss the approach and avoid duplicate effort.

Setting Up the Project

Step 1: Fork and clone

# Fork on GitHub, then clone your fork
$ git clone https://github.com/YOUR_USERNAME/idtrack.git
$ cd idtrack
$ git remote add upstream https://github.com/theislab/idtrack.git

Step 2: Install dependencies with Poetry

$ make install

This installs IDTrack in development mode with all dependencies.

Step 3: Verify your setup

# Start an interactive Python session
$ poetry run python

# Or run the CLI
$ poetry run idtrack --help

Step 4: Install pre-commit hooks (recommended)

$ nox --session=pre-commit -- install

This automatically runs code formatting and linting checks before each commit.

Note

See Installation for additional requirements like HDF5 on Apple Silicon.

Running Tests

IDTrack uses pytest for testing and Nox for test automation.

Run the Full Test Suite

$ nox

This runs all tests, linting, and type checking.

Run Specific Test Sessions

List available sessions:

$ nox --list-sessions

Run the default test suite (everything except tests marked slow; network-backed integration tests skip themselves when Ensembl is not reachable):

$ nox --session=tests

Run tests with a specific Python version:

$ nox --session=tests --python=3.12

Run Tests Directly with pytest

For faster iteration during development:

# Run all tests (slow-marked tests are skipped by default)
$ poetry run pytest

# Include slow tests
$ poetry run pytest --runslow

# Run a specific test file
$ poetry run pytest tests/unit/test_api.py

# Run the HTTPS-dump integration tests (they need only HTTPS access to Ensembl)
$ poetry run pytest --runslow tests/integration/test_ensembl_ftp_fallback.py

# Run tests matching a pattern
$ poetry run pytest -k "test_convert"

# Run with verbose output
$ poetry run pytest -v

# Run with coverage report
$ poetry run pytest --cov=idtrack --cov-report=xml --cov-report=term

# Run with coverage report (including slow tests)
$ poetry run pytest --runslow --cov=idtrack --cov-report=xml --cov-report=term

Test Organization

Tests are located in the tests/ directory:

tests/
├── conftest.py               # Shared fixtures (among them the graphs of real organisms) and markers
├── _real_tables.py           # Serves real Ensembl tables, cut down to a few hundred genes, to DatabaseManager
├── data/real/                # Per organism: the cut tables, the gene list, the expected answers, the build script
├── test_main.py              # Command-line entry point
├── test_external_mappers.py  # External mapping backends (slow classes query live services)
├── unit/                     # Offline tests, one file per module (test_api.py, test_db.py, ...) and test_real_*.py
└── integration/              # Network-backed tests against Ensembl (MySQL and HTTPS dumps)

Markers: slow (skipped unless --runslow or IDTRACK_SKIP_SLOW=0), network, integration, database and wrong_argument_type (a test that passes an argument of a wrong type on purpose; skipped in the typeguard session, where typeguard refuses the argument first).

The tests that can catch a wrong mapping are tests/unit/test_real_*.py. They need no network: tests/_real_tables.py serves real Ensembl tables of pig and human, cut down to a few hundred genes (tests/data/real/<organism>.tables.json.xz, each under 500 kB), to idtrack.DatabaseManager, so the graphs of both organisms are built by the production code (tables, history, graph file, engine, API) in the test session. Conversions are compared with expected answers that were derived from Ensembl’s own files (tests/data/real/<organism>.truth.jsonl) and with the tables themselves, read by independent code; the package’s self-tests (idtrack.TrackTests) run on the same graphs.

To write a table file again from a gene list (tests/data/real/<organism>.genes.txt), for example after adding genes that a new test needs:

$ poetry run python tests/data/real/build_real_tables.py --organism sus_scrofa --repository <local repository>

It reads the tables from the local repository and downloads what the repository lacks over HTTPS. tests/integration/test_real_tables_source.py (--runslow, network) fetches one release of each organism again and compares it with the stored file.

Building Documentation

IDTrack uses Sphinx with nbsphinx to build documentation from reStructuredText files and Jupyter notebooks.

Install Documentation Dependencies

$ pip install -r docs/requirements.txt

Build the Documentation

$ cd docs
$ make html

The generated HTML files are in docs/_build/html/. Open index.html in your browser.

Live Preview During Editing

For automatic rebuilds while editing:

$ pip install sphinx-autobuild
$ cd docs
$ sphinx-autobuild . _build/html

Then open http://localhost:8000 in your browser.

Note

IDTrack itself must be installed for the API documentation to build correctly. Notebooks are not executed during builds (nbsphinx_execute = "never"); they are rendered with pre-existing outputs.

Documentation Guidelines

When contributing to the documentation website:

  • Keep pages scannable: start with a short summary, then use .. contents:: and tables for structured material.

  • Prefer cross-links over duplication: use :doc:`...` for pages and :meth:`...` / :class:`...` for API items.

  • Tutorial notebooks are source of truth for narrative workflows: notebooks live in docs/_notebooks and are rendered by nbsphinx without execution during builds.

  • Avoid huge notebook outputs: keep outputs concise and deterministic so the rendered docs remain readable.

  • Outputs come from running the code: after changing a notebook, run it in full (with the graphs of the pinned snapshot release the tutorials use, 115) so that every shown output is what the code prints; never edit an output by hand. The examples of Quickstart and the README show outputs of the same snapshot.

Step-by-Step Guide

Step 1: Fork and clone

# Fork on GitHub, then clone your fork
$ git clone https://github.com/YOUR_USERNAME/idtrack.git
$ cd idtrack
$ git remote add upstream https://github.com/theislab/idtrack.git

Step 2: Create a feature branch

$ git checkout main
$ git pull upstream main
$ git checkout -b feature/your-feature-name

Use descriptive branch names:

  • feature/add-zebrafish-support

  • fix/hgnc-download-timeout

  • docs/improve-quickstart

Step 3: Make your changes

  • Write clear, focused commits

  • Follow the existing code style

  • Add tests for new functionality

  • Update documentation if needed

Step 4: Run tests and linting

$ nox

All tests and checks must pass before submitting.

Step 5: Push and create a pull request

$ git push origin feature/your-feature-name

Then open a pull request on GitHub against the main branch.

Pull Request Guidelines

Your pull request should:

  • Pass all tests - The Nox test suite must pass without errors

  • Include tests - Add tests for bug fixes and new features

  • Update documentation - If your changes affect user-facing behavior

  • Have a clear description - Explain what the PR does and why

  • Reference issues - Link to related issues (e.g., “Fixes #123”)

Code Style

IDTrack follows these conventions:

Aspect

Convention

Formatting

Black, line length 120, and isort (applied by the pre-commit hooks)

Linting

flake8 with flake8-docstrings, darglint, flake8-bugbear, flake8-bandit, flake8-rst-docstrings and pep8-naming (.flake8), pyupgrade --py312-plus

Type hints

Type annotations for public APIs; mypy (nox --session=mypy)

Docstrings

Google style (docstring-convention = google); every argument, return value and raised error documented (darglint checks it); cross-references with the :py:meth:, :py:class: … roles

The pre-commit session (nox --session=pre-commit) runs all of these.

Example Function

A docstring in the style of the package (modelled on idtrack.API.valid_final_databases()):

def valid_final_databases(self, to_release: int | None = None) -> list[str]:
    """Return the values accepted as ``final_database`` for a target release, sorted.

    These are the external databases of the genome assembly that is primary at *to_release* and the two
    Ensembl gene namespaces (versioned ``ensembl_gene`` and ``base_ensembl_gene``).

    Args:
        to_release (int | None): The target release; ``None`` means the graph's snapshot release.

    Returns:
        list[str]: The database names.
    """

Adding Organism Support

An organism is declared in one place, the organism table DB.assembly_mysqlport_priority in idtrack/_db.py; everything else (supported organisms, assembly node types, assembly priorities) is derived from it. Rhesus and cynomolgus macaque were added this way. The recipe:

  1. Establish the assemblies. List the organism’s core databases in Ensembl’s dump listings (https://ftp.ensembl.org/pub/release-<n>/mysql/): each is named <organism>_core_<release>_<code>[patch letter]. Read each assembly’s name from the meta table (assembly.default) and note the first and last release of each code. Check that every release has one assembly (a clean handoff) or note where two overlap (as human GRCh37 and GRCh38 do).

  2. Write the table entry. One entry per assembly, keyed by an integer that is unique within the organism:

    "macaca_mulatta": {
    10: {"Name": "Mmul_10", "Ports": [3306, 5306], "Priority": 1, "ReleaseRange": [98, None]},
    801: {"Name": "Mmul_8.0.1", "Ports": [3306, 5306], "Priority": 2, "ReleaseRange": [86, 97]},
    1: {"Name": "MMUL_1", "DbSuffix": "10", "Ports": [3306, 5306], "Priority": 3, "ReleaseRange": [48, 85]},
},

    The key equals Ensembl’s code where that is unambiguous. Where Ensembl reuses a code for two assemblies of the organism (rhesus _10 is MMUL_1 up to 85 and Mmul_10 from 98), the earlier assembly gets its own key and names the shared code in DbSuffix; their ReleaseRange values must not overlap. Ports are the public MySQL ports in preference order (3306 and 5306 serve release 48 onwards; 3337 is the GRCh37 archive and may be listed for human GRCh37 only, see DB.mysql_port_assembly); Priority 1 is the preferred, newest assembly. Add the organism’s symbol databases to DB.symbol_databases (e.g. ("VGNC Symbol", "HGNC Symbol")) and its short names to DB.organism_aliases (lower case, unique across organisms, e.g. ("rhesus",)). The table is validated at import. IDTrack reads Ensembl ids with versions: an organism whose ids carry no versions is not supported.

  3. Try it without editing the package. idtrack.DB.register_organism(name, assemblies, symbol_databases, aliases) adds the same entry for the running Python session, validates it, and recomputes everything derived from the table.

  4. Make the externals file. Generate the template over every release and form (DatabaseManager.create_database_content() and ExternalDatabases.create_template_yaml()), switch on the allowlisted databases with idtrack._default_externals.apply_allowlist (add the organism’s allowlist to DEFAULT_EXTERNALS there and to tutorial 02), and ship <organism>_externals_template.yml and <organism>_externals_modified.yml in idtrack/default_config/. See Part 2 — External Database Configuration. When Ensembl publishes a new release, extend the shipped files with ExternalDatabases.extend_modified_yaml instead of regenerating them.

  5. Teach the tests. Add a row per assembly to EXPECTED_RANGES in tests/integration/test_ensembl_ftp_fallback.py and the organism’s defaults (assembly, release window, seed genes) to REAL_GRAPH_DEFAULTS in tests/conftest.py. The unit tests check the table, the allowlist and the shipped files; the live MySQL tests check ports and releases where MySQL is reachable.

  6. Document it. Add the organism to the Supported Organisms table in Quickstart and to the tutorials that list organisms.

  7. Validate and submit. Build a small graph across each assembly handoff, convert known identifiers, and open a pull request with the table entry, the externals files, the tests and the docs.
